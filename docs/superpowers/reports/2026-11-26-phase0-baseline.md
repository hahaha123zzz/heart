观察：

- **`check_active_turn` 与真正接收不一致。** 每次首问 `done` 后 0.03–0.045 秒，`check_active_turn`
  已返回 `status=none`；但同会话第二问仍连续收到 `start_turn_rejected`（“Session already has an active
  or recovering turn”），直到 done 后 1.97–7.95 秒、重试 3–4 次才被接收。持久化回合终态与协调租约释放
  不同步，计划里“活跃检查为 none 仍遭拒”的现象可稳定复现，并非偶发。
- 明确引用小节的题检索量最大：9 次工具、23 条来源、17,783 字符、输入 49,707 Token；首问 23.81 秒，
  第二问 44.52 秒（第二问没有首问的预检索缓存）。
- 无教材证据题没有来源，10.67 秒完成；没有出现编造来源。
- 部分回合的终止 `done` 事件不带 `cost_summary`，Token 只能从另一个带摘要的事件取得；无证据题首问没有可读
  Token，第二问有 7887 输入 / 1275 输出。Token 采集目前是“有则记、无则空”，不能保证每回合都有。
- 问候题也发生了 1 次工具调用；工具名未记录（只有数量），需要时再补。

- 摘要触发一次约 17 ms（不含远端模型调用本身），有效旧摘要下只保留 12 条近期消息。
- **分支重答无法在这条路径上采样**：宿主历史适配器 `_HistoryStore.get_messages_for_context` 忽略
  `leaf_message_id`，总是返回全部行。计划要求的“分支”覆盖需要先补宿主适配器，不能只靠采样。

## 5. 现有观测缺口

1. **逐回合的检索分段没有记录。** 固定教材路径不写 `course_search_timing`（该日志只在旧的
   `course_search_api`），worker 的 `heart.native_timing` 也没有输出 `native_turn` 行。因此本轮只能拿到
   事件级里程碑（首个正文/工具/来源/完成），拿不到“检索排队、关键词、向量、重排、来源校验与组装”的
   逐项秒数。要满足计划第 3 项的这一半，需要给固定教材检索加一条按回合的计时记录（并带会话/回合标识）。
2. 进程间对齐目前只有 `startup_id`；回合级标识缺失，无法自动把宿主/worker 记录并到同一回合。
3. Token 只在部分回合出现；工具名未记录。
4. 启动时间对机器缓存敏感，单轮样本不能比较不同日期的绝对值。

- 启动编排的收益已在冷缓存下确认：worker 先行让宿主可用时间从 93.84–122.77 秒降到 43.67–44.22 秒。
- 发行核对不再逐文件哈希：热缓存下三个服务合计 4.4–5.9 秒，冷缓存下 23.8–29.2 秒；旧实现单次全量哈希

- 回答阶段的主要成本在检索与工具往返：原题 4 条来源用了 15.6 秒（首个工具到来源），引用小节题
  23 条来源用了 21.4 秒；GPU 重排已把单次重排从 11 秒级降到 0.1–0.7 秒，剩余时间在检索排队、
  证据组装和模型调用。
- 连续追问的真实可接收时间比 `check_active_turn` 晚 2–8 秒；阶段 2 若做回答延迟优化，应优先修
  协调租约释放或让前端在 `start_turn_rejected` 上自动重试，而不是只改检索。
