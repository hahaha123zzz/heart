## 3. 本轮实际embedding CPU/CUDA测试

脚本：`.runtime/latency-deep-audit-20261025/probe_embedding.py`。使用项目已有 `.venv-gpu`，同一BAAI/bge-small-zh-v1.5权重、threads=4、三条合成短问题；离线、本地文件、无教材/学生数据；每设备独立进程，预热后5次batch=3。未修改业务代码或服务配置。

| 项目 | CPU | CUDA |
| --- | ---: | ---: |
| 模型构造 | 0.221秒 | 8.500秒 |
| 首次三条推理 | 0.0138秒 | 115.266秒 |
| 五次预热后三条推理中位 | 0.00406秒 | 0.01217秒 |
| 实际会话provider | CPUExecutionProvider | CUDAExecutionProvider + CPUExecutionProvider |

三组向量余弦相似度均大于0.9999998，最大元素绝对差约0.000089。CUDA会话确实完成了推理，但并未证明所有算子都在GPU；ORT提示部分节点分配CPU，这是其图划分行为，不等于整体回退。

**结果：本次短查询embedding上GPU约慢8毫秒，不能作为首要提速手段。**首次运行还暴露明显冷启动成本；未细分CUDA首次编译、内核初始化和运行时间，不将115秒全部归为某个已证实原因。只有一次冷运行，不能承诺下次相同耗时。

机器RTX5060 Laptop约8GB显存，资源快照系统RAM可用约1.6GiB。没有额外加载大型reranker，避免影响其他窗口。reranker GPU性能尚未实测；它与小embedding、短查询的计算规模不同，不能套用本次结论。现有GPU环境能启动CUDA会话，但CPU/GPU ONNX包元数据共存，正式部署仍需确认实际导入版本和依赖一致性。

## 4. DeepTutor速度相关优势与宿主现状

| 上游代码 | 做法 | 相对宿主的价值/限制 |
| --- | --- | --- |
| `deeptutor/agents/loop/pipeline.py:1481` | 传统知识库先有界预取，独立KB并发 | 少一轮是否检索的决策；main已适配部分流程，8000未统一使用提速链 |
| `runtime/agentic/client.py:234` | 有界、事件循环隔离的连接池与资源关闭 | main已有同步传输适配，不能再新增第二套；只池化网络传输，不共用学生状态 |
| `runtime/agentic/tool_dispatch.py:288` | 先串行目标重绑定，再普通工具并行，最后暂停工具 | 比“所有工具一律并行”更成熟；宿主已有普通工具线程并行，但需重点核对路径/目标变更工具的依赖顺序 |
| `agents/loop/pipeline.py:477`和约1625行 | 单轮系统提示稳定，控制上下文并裁剪过旧工具输出 | 提高缓存利用、减少输入负担；宿主不能直接裁掉待答/引用协议或当前目标证据 |
| `services/rag/pipelines/lightrag/roles.py:96` | keyword/query等角色各自模型选择、并发和超时 | 有利于简单角色使用更合适模型；宿主当前多角色共用一个LLMClient，角色路由更粗 |
| `services/embedding/client.py`及adapters | provider统一抽象、分批与调用节流，Ollama有keep_alive | 执行位置由服务决定，不是自动GPU化；频繁新客户端也并非上游所有adapter都已消除 |
| `services/rag/pipelines/lightrag/pipeline.py:609` | build/initialize/query/finalize | 也逐请求执行，不能用“复制上游常驻池”解决一个上游没有现成实现的问题 |

上游native engine使用aquery_llm，宿主使用aquery_data避免检索内部再生成一次答案；整套照搬上游会增加内层生成风险。上游代码能复用编排、缓存和角色策略，不能据此证明其在本机同题端到端更快。

## 5. 哪些可以省，哪些不能直接省

### 确定应消除或避免

- 8000旧发布的同查询第三次完整校验、重复宿主清单遍历；main已减少，应采用现有稳定代码。
- 已有明确教材目标/图号/选区时先全书图检索；复用Q2精确读取和Q4 read_material/read_source。
- 同请求同身份同范围的等价重复检索、重复选证与覆盖判断；main已有本请求复用和合并决策，不重复实现。
- 为常规工具调用重新建立网络传输、无关会话持有同一引用全局锁；main已有改造。
- 固定教法/已确认活动仅为登记状态再耗一轮模型的候选优化：先量化真实调用，再评估服务端确定性登记。不能伪造“模型已讲解”、推断理解或绕过最终正文检查；教学需要自主选择工具时仍保留模型决策。

### 是成本，但不是可无条件删除的冗余

- 来源/版本核验、查询期间变化拒绝、图像身份验证、最终事实检查。
- 缺一侧的有界补查；直接省掉将恢复之前跨章漏检。
- 原文重排：可以限候选数、优先精确目标或加速，不能不验召回/精度就删掉。
- 前后内容校验：优先请求内复用。跨请求缓存只能基于有可信不可变所有权的版本快照；仅mtime/size缓存无法保持防篡改契约。
- 两次角色不同的模型调用（选证 vs最终事实核查）不能因都用LLM就判为重复。

另有可优化点：`grounded_citations.py::EvidenceBundle.references`按每条引用重复读取对应PDF并计算SHA，`citation_index.py`也有同文档身份核验与最多2个_live_document缓存。可按**本请求/本发布阶段的文档身份**去重复读取；保留最终时间点的真实文件核验。跨多章可能产生LRU淘汰，但未测到具体命中率，不建议直接增大全量PDF缓存（当前内存紧张）。

## 6. 换模型、方式或GPU：分别处理

| 环节 | 推荐方向 | 验收边界 |
| --- | --- | --- |
| CPU reranker | 最优先GPU单项对照；必要时按对象限候选和截取真实相关范围 | 同权重/来源/阈值，检查排序和双侧覆盖；预热后比较，不能静默CPU回退 |
| 查询embedding | 暂保CPU；批量摄取另测GPU | 本轮短问题GPU未改善，不影响离线大批量结论 |
| keyword提取、原文选证 | 复用上游角色选择接口，测试更低延迟且支持稳定JSON的模型 | 先测错误率/漏检，再比较时间与费用；建图extract身份和查询角色分开，不改embedding模型重建索引 |
| 最终质检 | 检查器按任务使用合适模型；普通文本不附无关图像/证明审计 | 真实事实错误、错误引用、图像错误必须可拦截；不能仅测通过样本 |
| 正文生成 | 控制不必要上下文和输出长度，保持普通任务非推理模式 | 宿主已有关闭DeepSeek思考逻辑，不能宣称新开关；复杂推导按需保留能力 |
| 图检索/精确阅读路由 | 定位/继续/读图走现有目标和精读；跨章关系问题再图查询 | 不新增僵硬关键词路由导致问题范围错误；先解决输入目标再检索 |
| 文件/PDF | 请求内按文件身份复用、消除逐引用重复、补未观测阶段 | 不改来源原文、版本、rects，不使用本机GPU做磁盘哈希 |

本轮没有对新模型做真实调用对照，不推荐未经验证的具体模型名、价格或承诺倍数。DeepTutor角色分工是可迁入能力，不代表轻量模型一定能可靠选证/判错。

## 7. 并行执行的可行性

| 工作 | 能否并行 | 必要条件 |
| --- | --- | --- |
| 独立目录/画像/课程状态读取 | 可以 | 同一请求只读快照、权限隔离，合并后统一决定目标 |
| 不同文件的哈希/资产元数据准备 | 可有界并行 | 限线程数，测磁盘竞争；保留最终变更核验，不假设线程越多越快 |
| 不同独立KB查询 | 可以 | 存储和授权独立，上游预取已用gather |
| 同一LightRAG候选的两次原生查询 | 当前不能直接并行 | 候选所有权保护会串行/拒绝；不能删锁冒充只读并发 |
| 对象A已完成检索后的选证 + 对象B的检索 | 可以尝试流水线 | A的来源/指标冻结，B获得候选锁；最后统一覆盖、去重和编号；任务取消贯穿两边 |
| 已取得独立证据的两对象选证 | 可以有界并行 | 各自限制来源ID/范围，最终统一缺口判断；没有两对象时不制造并行任务 |
| 媒体准备与独立的引用格式检查 | 部分可以 | 必须先确定实际媒体及版本，不在未知图片时开始视觉质检 |
| 固定正文的教学事实检查与证明检查 | 已有并行 | QualityChecker已有线程池；心理学普通题不增加证明检查 |
| 正文生成与完整最终事实质检 | 不能直接并行 | 后者需要完整正文；可以流式展示有证据正文，但正式保存仍待核验 |
| 路径切换、推进与其他工具 | 不应无序并行 | 上游先rebinding再普通工具，避免旧目标状态竞态；保留revision/幂等 |
| ask_user 与普通工具 | 暂停最后 | 复用现有协议，问题卡展示的是本轮最终状态 |

候选查询独占锁并非所有步骤都必须串行。优先尝试对象选证/后继检索流水线，而非重写原生存储并发或增加进程数；后者可能复制CPU模型、扩大内存压力。

## 8. 优先级与后续最小实验

1. 合入并部署统一main/Q4/图片版本，固定一个实际宿主。不能继续将main已解决问题算成新增开发。
2. 补齐最终41秒轨迹约13秒未归属区间的计时，并对**实际部署版本**跑少量隔离同题采样；同时记录CPU占用、可用内存与候选数，不修改正式学生状态。
3. 独立测reranker：同候选文本，CPU/GPU冷启动、预热、batch=1/4；同时检查排名和结果一致性。再决定是否只切reranker，不默认embedding一起切。
4. 按文档去重复PDF核验、限候选并保留覆盖；优化前后均测双章和缺证负例。
5. 再做对象流水线与角色模型对照；先低风险关键词/选证，再最终质检。保留错误率/引用覆盖，不能只比较秒数。
