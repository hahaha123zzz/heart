# 甲方需求与当前项目差距评估

日期：2026-10-12。

## 评估依据与边界

- 甲方文件：`实验心理学课程智能体平台.docx`，标题为《实验心理学》智能体教学平台功能，包含八项功能及基础、进阶阶段划分。
- 补充资料：用户提供的《已粘贴的文本.txt》，内容为教学决策、错误诊断、工具、评测等研发建议。它作为讨论材料，不视作甲方新增验收要求；本次没有核验其中论文、第三方仓库和许可声明。
- 实现依据：当前工作区代码，包含 `aedc6e1` 之后尚未提交的任务理解和交互更新。
- 当前可运行应用位于 `project/integration/discrete-math-tutor`。外层 `project/server` 是原平台模块抽取版，缺少原平台数据库、鉴权、课程与知识服务，不能计作已交付的完整心理学平台。
- 本次为文档、代码和本地题库数据审查；没有重新执行真实模型、浏览器、并发或真实学生效果测试。既有测试报告仅用于说明已验证的范围。
- 课程交付范围尚待确认：如果最终按甲方文件交付实验心理学，课程资料与领域规则转换是 P0；如果离散数学是经甲方认可的通用能力验证 Demo，这一项属于后续迁移工作。

## 核心判断

当前项目已有教材阅读、检索问答、图文证据、结构化练习、教学策略、跨会话记忆和显式偏好设置。主要不足集中在教师侧交付、正式账户及长期数据、可靠测评覆盖、学生错误诊断与教学效果验收。

教学决策层已有 `TeachingPolicy`、`TeachingPlanner`、`QuestionDesigner` 和 `TaskExecution`；应在现有链路上增强诊断、策略约束和结果检验。模型生成的规划或质量检查通过，不能单独证明学生已掌握知识。

## P0：优先补齐可交付功能

### 1. 正式账户、班级及长期记录

网页由 localStorage 生成 `demo-*` 学生ID，聊天请求固定发送 `account_type: "test"`。测试账户24小时过期；代码指纹变化也会清理测试记录。后台存在 production 持久化路径，但网页若干接口仍强制创建测试账户，记忆管理拒绝 production 账户。因此不能只修改一个请求参数就完成正式化。

先统一服务端登录身份、学生/教师角色、班级关系与正式账户生命周期，再接入所有阅读、练习、设置及记忆接口。测试清理应限于明确的演示环境。

验收场景：两个学生的记录分别保存；服务重启、代码更新及下一天登录后，正式记录仍在；教师只查看其班级；学生不能通过替换请求中的ID操作其他学生。

### 2. 教师端的最小统计页面

直接围绕甲方基础功能交付：班级资源使用、章节学习进度、测验完成与成绩、常见错题。先复用现有记录及提交表补聚合接口，明确班级成员分母、时间范围和数据口径。

资源浏览、练习完成和知识掌握分别展示。当前资源表只有章节、小节和打开时间；若需要阅读完成率，补充页码进度或明确完成事件，不能用一次打开替代完成。

验收场景：一名教师、一个班级、数名学生，各产生不同浏览和作答记录；教师汇总与逐条原记录一致，错误率与未提交人数可核对。

### 3. 甲方认可的课程资料与正式测验

若交付实验心理学，先用一个真实章节完成纵向样板：教材、课件、实验装置或结果图、课程题库、出处。梳理可配置的课程标识、章节、知识点及领域提示，避免只改页面标题。当前很多生成约束和评分工具明确面向离散数学。

若仍验收离散数学，也需明确课件是甲方未提供，还是产品缺少导入/发布能力；缺资料与缺功能应分别登记。

正式测验先选择教师认可、答案与评分标准明确的一组题。客观题确定性评分；主观题保留辅助评价，并补教师复核、修订成绩及审计记录。当前 `needs_review` 是状态标记，未形成教师处理流程。

验收场景：从章节资料进入测验，提交得到评分与出处；未确定的反馈不自动进入可靠成绩；教师复核后的结果能回到学生页面与统计。

## P1：优先增强已有教学链路

### 4. 学生错误步骤诊断

当前 `ProofChecker.check(response, question, textbook_excerpts)` 检查的是助教生成的证明。练习批改虽要求模型逐步检查并返回反馈，尚未形成逐条绑定学生原句、定位首个错误、区分错误类型、验证具体反例的统一诊断结构。

建议增加学生作答诊断结果：学生原句/步骤ID、正确/错误/未知、违反的条件、可核对依据、下一步提示。先选集合、关系、真值表等可确定性验证的场景，复用已有规则和SymPy；复杂自然语言证明保留待确认，不能把模型评审等同形式证明。

若迁移实验心理学，应对应实验设计、变量与操作化、混淆因素、方法选择、结果解读等错误，数学工具只能复用工程边界，不能直接承担领域诊断。

验收重点：错误位置是否正确、错误原因是否有证据、能否接受另一种正确方法、提示是否泄露完整答案。

### 5. 教学决策的行为验收与可追溯记录

`TeachingPlan` 已有 goal、strategy、action、difficulty、hint_level、expected_student_behavior、rationale，补充文字中的新接口大部分可在此扩展。

先验证明确规则：查定义时给定义；只要提示时不泄露结论；连续受挫时适度转示范；自述懂了时可给小检查；学生明确要完整解释时尊重请求。每轮保存实际采用动作、触发证据、回退原因和版本，检查Planner输出与最终回答是否一致。

验收使用同一问题与不同学生状态的对照，避免只统计策略名称是否输出合法。

### 6. 主动练习与复习任务

复用已有学习事件、技能观测、误区状态和题库，补充复习任务及状态：目标知识/技能、来源证据、推荐题目、到期时间、提示使用、独立作答结果和后续安排。

先实现一条完整体验：独立作答错误 → 解释与提示 → 新题独立检查 → 下次会话提醒 → 复测结果更新建议。学习者可跳过复习、纠正记录或直接索取讲解。获得提示后的作答继续与独立测量区分。

时间调度是可以逐步增加的产品能力，甲方并未指定必须使用FSRS或任何特定遗忘模型。

### 7. 冻结多轮教学质量基线

现有单元测试、浏览器替身及少量真实API回归说明部分工程流程有效；不能替代真实教学质量或独立学习结果评测。

先冻结一批由教师审核的真实教材场景，覆盖查定义、仅提示、概念混淆、错误证明、反复受挫、迁移题和跨会话复习。评价三层：

- 回答：事实正确、证据充分、引用可定位。
- 教学：错误定位、动作合适、无无效追问、无提示越界。
- 学习：未使用AI的独立作答、迁移与延迟复测。

保留新题验收与开发回归的区分，记录整轮延迟和失败原因。已有少量真实回答报告耗时十几至几十秒，需在真实使用场景测量P50/P95与并发，再决定是否合并调用或缓存。

## 建议执行顺序

1. 确认课程交付范围，同时打通正式学生与教师身份、班级、记录保存。
2. 交付教师基础统计及一组可信的正式测验，补待复核处理流程。
3. 冻结教学验收场景，增强现有诊断与教学决策；同步验证提示、解释、受挫切换。
4. 打通新题独立检查与下次会话复测，再扩大图文、评分和技能覆盖。
5. 在真实样本上校准画像、评估教学效果后，考虑模拟学生优化与更重的框架或训练。
